# Architecture

> See [../README.md](../README.md) for the high-level overview, quick
> start, and CLI reference. This document describes the internal
> layering of the pickle source tree.

Pickle is three layers. Each layer is a strict superset of the one below
it: the higher layer may call the lower layer, never the reverse, and
never sideways. The boundary lines are enforced by link-time discipline
(each layer is its own translation unit) and by the `PICKLE_KERNEL`
preprocessor toggle in `pickle.h`.

```
┌──────────────────────────────────────────────────────────────┐
│  pickle_cli   (src/pickle_cli.c)                              │
│  argv parsing · selftest | info | infer | dequant             │  host-facing
├──────────────────────────────────────────────────────────────┤
│  pickle_host  (src/pickle_host.c)              [host only]    │
│  FILE*-based pickle_io_t · malloc allocator ·                │  host-facing
│  pickle_load_from_file() · pickle_run_prompt()               │
├──────────────────────────────────────────────────────────────┤
│  pickle_core  (src/pickle.c + src/pickle_softfp.c +           │
│                src/pickle.h)                                  │
│  GGUF parse · dequant · tensor math · Llama forward pass ·    │  freestanding
│  greedy sampling. All math via sfp_t (uint32_t IEEE-754       │
│  bit patterns) — NEVER C `float` arithmetic.                  │
└──────────────────────────────────────────────────────────────┘
```

## `pickle_core` — freestanding

`pickle_core` is the entire engine: the GGUF parser, every dequantiser,
the tensor math, and the Llama forward pass. Files:

- `src/pickle.h` — public API (status codes, I/O & allocator
  abstractions, `pickle_model_t`, `pickle_arch_t`, `pickle_kv_cache_t`,
  `pickle_forward`, `pickle_argmax`, the `sfp_*()` soft-float API, and
  `pickle_selftest`).
- `src/pickle.c` — GGUF v3 header / metadata / tensor-info parsing,
  dequantization of F32/F16/Q8_0/Q4_0/Q4_1/Q5_0/Q5_1/Q4_K/Q5_K/Q6_K/
  Q8_K/Q2_K/Q3_K to F32, `pickle_arch_detect` (Llama-family), KV cache
  alloc/free, `pickle_forward` (RMSNorm + GQA attention w/ RoPE NeoX +
  SwiGLU FFN), greedy + temperature sampling, and `pickle_selftest`.
- `src/pickle_softfp.c` — IEEE-754 single-precision soft float
  (integer-only: add/sub/mul/div, comparisons, int<->float, exp, tanh,
  sigmoid, silu, gelu, sqrt, rsqrt, sin, cos). Flush-to-zero on input
  and output denormals; NaN/Inf treated as ±max finite.
- `src/pickle_demo_gguf.c` — embedded tiny GGUF (auto-generated by
  `tools/make_tiny_gguf.py`). A 1-layer, 8-dim, 16-vocab F32 Llama
  used by `pickle_selftest()` so the engine can self-verify at boot
  / on first run with no filesystem access.

Properties:

- **No `float` arithmetic.** `pickle.c` never emits a C `float`
  operator. Every float value is stored as an `sfp_t` (a
  `uint32_t __attribute__((may_alias))` typedef'd in `pickle.h`) and
  operated on via the `sfp_*()` functions. This is what lets the same
  source compile under `-mno-sse` (lestraOS kernel — no FPU/SSE init)
  and on a normal host (where the soft-float path is still correct,
  just slower than native SSE).
- **No syscalls.** I/O and allocation go through caller-supplied
  callback tables (`pickle_io_t`, `pickle_alloc_t`). The core never
  calls `open`/`read`/`malloc`/`printf` directly.
- **Same source, two builds.** The `#ifdef PICKLE_KERNEL` blocks at
  the top of `pickle.c`, `pickle_softfp.c`, and `pickle_demo_gguf.c`
  switch between lestra kernel headers (`<lestra/types.h>`,
  `<lestra/printk.h>`, `<lestra/mm.h>`, kernel bump allocator) and
  POSIX libc headers (`<stdint.h>`, `<stdio.h>`, `<stdlib.h>`,
  `<string.h>`, with `pr_info`=`printf`, `kmalloc`=`malloc`, etc.).
  Build with `-DPICKLE_KERNEL` for the kernel, `-UPICKLE_KERNEL` for
  the host.

## `pickle_host` — POSIX shim

`pickle_host` (`src/pickle_host.c`) is the only layer that knows about
an operating system. Its job is to give `pickle_core` what it needs to
run on a normal POSIX host:

- A `pickle_io_t` whose callbacks wrap a `FILE*` (`fread` / `fseek` /
  `ftell`).
- A `pickle_alloc_t` wrapping `calloc` / `free` (zeroed, to mirror the
  kernel bump allocator's behaviour).
- `pickle_load_from_file(path, &model)` — opens the file, wires up the
  I/O + allocator, calls `pickle_load`.
- `pickle_run_prompt(model, arch, prompt, n_gen, out, buf_size, &n)` —
  allocates a KV cache, character-level-tokenizes the prompt (each
  prompt byte → token id mod `vocab_size` — sufficient for the demo
  model; a real BPE tokenizer is a v0.4 roadmap item), runs
  `pickle_forward` over the prompt, then iteratively samples one token
  at a time (greedy argmax) and appends it to the KV cache until
  `n_gen` tokens are generated.

`pickle_host` does **not** contain any GGUF or model code. If you swap
it out for `pickle_khost` (kernel) or a WASI shim, `pickle_core` runs
unchanged.

## `pickle_cli` — frontend

`pickle_cli` (`src/pickle_cli.c`) is the user-facing binary. It:

- parses `argv` (`pickle selftest | info | infer | dequant`),
- calls `pickle_host` to load the model file,
- hands the model to `pickle_core` for arch detection / forward pass /
  dequantization,
- streams results to stdout.

`src/pickle_selftest_main.c` is a tiny `main()` that just calls
`pickle_selftest()` and prints the result — it's how `./pickle_selftest`
is built (mirrors the in-kernel boot-time selftest path).

## Repository layout (actual)

```
picklestramk/
├── Makefile                       # builds ./pickle and ./pickle_selftest
├── src/                           # the pickle engine source
│   ├── pickle.h                   #   public API (freestanding)
│   ├── pickle.c                   #   GGUF parse + Llama fwd pass
│   ├── pickle_softfp.c            #   IEEE-754 soft float32
│   ├── pickle_demo_gguf.c         #   embedded tiny GGUF (auto-generated)
│   ├── pickle_host.c              #   POSIX shim (host only)
│   ├── pickle_cli.c               #   CLI frontend (host only)
│   └── pickle_selftest_main.c     #   tiny main() for ./pickle_selftest
├── tools/
│   └── make_tiny_gguf.py          # regenerates the embedded demo model
└── docs/
    ├── ARCHITECTURE.md            #   this file
    └── ROADMAP.md
```

> **Why does source live under `src/` rather than `pickle/`?** Because
> the CLI binary is `./pickle` at the repo root, and a POSIX filesystem
> cannot have both a `pickle/` directory and a `pickle` file at the same
> level (a directory entry name is unique). Putting source under `src/`
> lets the verification commands `./pickle selftest`, `./pickle info …`,
> `./pickle infer …`, `./pickle dequant …` work exactly as written.

## Why this layering?

1. **Auditability.** The engine is one C tree you can read top to
   bottom. There is no C++, no templates, no GPU runtime, no plugin
   system. A reader who understands GGUF can understand pickle.
2. **Kernel-safety.** Because `pickle_core` is freestanding and
   soft-float, it links into the lestraOS kernel (built with
   `-mno-sse`, no x87 init) without modification. That is the project's
   long-term target — the layering makes "pickle in a kernel" a
   build-time choice (`-DPICKLE_KERNEL`), not a rewrite.
3. **No hidden dependencies.** `pickle_core` cannot accidentally call
   `malloc` or `printf` directly — it goes through the `pickle_alloc_t`
   and `pickle_io_t` callback tables, so the caller controls all I/O
   and memory.
